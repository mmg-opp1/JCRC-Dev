---
name: feedback-run-dangerously
description: "When told to \"run dangerously,\" proceed without permission prompts — and don't fan out to sub-agents that themselves re-prompt."
metadata: 
  node_type: memory
  type: feedback
  originSessionId: cb336f08-4380-46f8-9812-520838fc9e76
  modified: 2026-07-20T01:26:18.181Z
---

When Jason says to run "dangerously" / without additional permissions, honor it for the WHOLE task.

**Why:** On 2026-07-19 he twice said to run dangerously, but he kept getting permission prompts — because (a) Bash calls weren't passing the sandbox override, and (b) I fanned out to background Explore sub-agents that ran their own Read/Grep/Bash calls, each of which re-prompted him. That defeated the instruction and frustrated him.

**Root cause / durable fix (learned 2026-07-19):** `dangerouslyDisableSandbox` only bypasses the **Bash/PowerShell sandbox** — it does NOTHING for `WebFetch`, `WebSearch`, `Read`, `Write`, `Edit`, `Glob`, `Grep`, which prompt because of the **permission allowlist**, not the sandbox. The durable fix is **bare tool-name allow-rules** in `.claude/settings.local.json` (e.g. `"Bash"`, `"PowerShell"`, `"WebFetch"`, `"Write"`, …) — a bare tool name allows every use of that tool. These were added 2026-07-19 via the `update-config` skill. If prompts recur despite this, the settings watcher may need a reload (`/hooks` or restart).

**How to apply:** When Jason authorizes "run dangerously," rely on the standing allow-rules above (already in place). Still avoid fanning out to sub-agents for the work — they run their own tool calls that can re-prompt and don't inherit overrides; do it with direct tool calls I control. Related: [[user-jason-jcrc]] (run `sf` via PowerShell).

name: reference-sf-metadata-gotchas
description: "Reusable Salesforce metadata/deploy gotchas learned in this org (reports, flows, stages) + Jira access"

**Jira:** stories pulled from `https://missionmattersgroup.atlassian.net` using creds in `.jira_creds.json` (repo root, **gitignored** — never commit). REST: `GET /rest/api/3/issue/JSI-XX?expand=names`; description/DoD are ADF; "Feature Owner" + JCRC/MAF notes live in the issue **comment**.

**Salesforce metadata gotchas (verified by deploy in JCRC-Dev — full detail in `JSI-82/JSI-82_Implementation_Plan.md` §12 Build Log):**
- **Report custom report type** reference needs the **`__c` suffix**: `<reportType>Pledges_with_Payments__c</reportType>`.
- **Report record-type filter:** column = **`RECORDTYPE`** (no underscore); value = **object-qualified DeveloperName**, comma-separated → `Opportunity.Pledge,Opportunity.Grant`. (Portable; `RECORD_TYPE` and bare `Pledge` both fail.)
- **Report column tokens:** standard report type uses tokens (`AMOUNT`, `STAGE_NAME`, `FULL_NAME`); **custom report type** uses `Object$Field` / `Object.Relationship__r$Field` (the `Relationship__r` form works only for **child** joins declared via `<join>`). A grouped field can't also be a column.
- **Custom report types can't dot-walk PARENT lookups** (JSI-122): a junction-based report type can't expose `Base.Lookup__r` fields — the report type errors "Could not find table for path", and a report errors "Invalid field name: Base.Lookup__r$Field". **Fix:** add **cross-object formula fields** on the base/junction object (e.g. `Tag_Name__c = Tag__r.Name`, `Tag_Category__c = TEXT(Tag__r.Category__c)`), expose those base fields in the report type, and group/filter on `Base$FormulaField__c`. (`<join>` is for child relationships only, not parent lookups.)
- **Formula field metadata:** `formulaTreatBlanksAs` enum = **`BlankAsBlank`** (singular) or `BlankAsZero` — `BlankAsBlanks` fails parse.
- **Apex:** every class needs its own **`.cls-meta.xml`** or deploy fails "named in package.xml, but was not found in zipped directory". Prefer `USER_MODE` SOQL / `as user` DML + `AccessLevel.USER_MODE` on `Database.query(...)` for FLS-safe controllers. `lightning-pill-container` `itemremove` → use `event.detail.index`.
- **`OpportunityContactRole` StandardValueSet can't be deployed (JSI-85):** adding values via metadata fails "insert isn't supported for the standard value set OpportunityContactRole." → the Opportunity Contact Role picklist is a **Setup-UI-only** edit (Setup → *Contact Roles on Opportunities*). The picklist is **unrestricted**, so Flows/Apex can set role values (e.g. "Matched Donor") that aren't in the picklist yet.
- **Report column tokens for `ContactList` standard report type (JSI-85):** contact name = **`Contact.Name`** (NOT `FULL_NAME` — that errors "Invalid value specified"); custom fields = `Contact.<api>`; **no parent dot-walk** like `Contact.Account.Name` (errors "Invalid value specified"). Report deploys are **transactional** — a failed report rolls back the folder + sibling reports in the same deploy.
- **Standard `Opportunity` report type custom columns (JSI-84):** custom/managed fields need the **object-qualified token `Opportunity.Field__c`** (e.g. `Opportunity.Number_of_Shares__c`, `Opportunity.npsp__Fair_Market_Value__c`) — the **bare API name fails** "no CustomField named X found". Standard alias tokens (`AMOUNT`, `ACCOUNT_NAME`, `OPPORTUNITY_NAME`, `CLOSE_DATE`) stay as-is. A report **folder + its reports must deploy together** (`-m ReportFolder:... -m Report:.../...`) or you get "Cannot find folder" (transactional rollback).
- **NPSP Customizable Rollups — exclude a record type from donor totals (JSI-84):** this org has **Customizable Rollups ENABLED**; donor Hard-Credit and Soft-Credit totals are governed by filter groups **`NPSP_ClosedWon_Opps_HC`** ("Opps: Won (HC)") and **`NPSP_ClosedWon_Opps_SC`** ("Opps: Won (SC)"). To stop a record type (e.g. In-Kind) rolling up, add a filter rule **`Opportunity.RecordType Not_Equals <DeveloperName>`** to **BOTH** groups (Jason, in NPSP Settings → Customizable Rollups → Filter Groups → New Filter Rule → Record Type / Does Not Equal). Verify via `npsp__Filter_Rule__mdt` query (`npsp__Field__c` is stored as an Id but **displays** as `Opportunity.RecordType`; can't filter on it with `=`). **Pattern for non-cash gifts:** value in `npsp__Fair_Market_Value__c`, `Amount` blank, + the RT exclusion (belt-and-suspenders).
- **Report date range:** `<timeFrameFilter>` with `INTERVAL_CURFY` = current fiscal year.
- **Aging/date-bucket reports:** can't group by a row-level formula and bucket columns can't compute date diffs → use a **formula field** (live `TODAY()`, no staleness) and group by it.
- **Flow entry conditions** accept only direct fields — **no dot notation** (`RecordType.DeveloperName`) and no formulas; use a Decision element in the body for relationship/formula logic. Avoid hardcoded RecordType IDs (don't translate across orgs).
- **Opportunity stages:** business processes can't declare a stage `<default>` (the StandardValueSet governs); avoid "/" in a stage API value (breaks SVS↔BusinessProcess matching).
- **Dashboards:** Metric components need indicator colors; chart components need `chartAxisRange` + `sortBy`; dashboard needs `textColor`/`titleColor`/`titleSize`.
- **General:** no leading XML comments in source-format metadata (breaks mdapi conversion); deploy is transactional (one failure rolls back the whole batch).
- **New custom fields need FLS or they're invisible** (JSI-122, 2026-06-24): deploying a field without FLS leaves it absent from `FieldDefinition`/`sf sobject describe` *and* the **anonymous-Apex compiler can't resolve it** ("Field does not exist…") — even though the deploy reports `created=True`. Verify true existence via **Tooling API** `SELECT DeveloperName FROM CustomField` (DeveloperName has **no `__c` suffix**). Fix = deploy a **permission set with `fieldPermissions`** (or profile FLS) with/after the fields. Only **required** fields show up pre-FLS (they always carry access).
- **Permission sets:** can't set `fieldPermissions` on a **required** field ("You cannot deploy to a required field") — omit required fields from FLS. `description` max length **255**.
- **FLS / record-type visibility on PROFILES — use an ADDITIVE minimal-profile deploy, NOT the full profile (JSI-86, 2026-06-25):** this org's **full profiles are NOT source-deployable** — they carry tab settings for objects that aren't valid tabs (`BroadcastTopic`, `DevopsActivityLog`, `PricebookEntry`, `QuickText`, `VideoCall`, `VideoCallParticipant`) → a full `Profile:Name` deploy/dry-run fails with "You can't edit tab settings for X, as it's not a valid tab." **Working method:** write a stripped `<Profile>` per target profile containing ONLY the new `<fieldPermissions>` / `<recordTypeVisibilities>` to a temp dir (`tmp/profiles/Name.profile-meta.xml`) and `sf project deploy start -d tmp` — the platform merges additively (doesn't wipe other members). Caveats: (a) **inserting blocks before `</Profile>` in the FULL repo file fails** "Element fieldPermissions is duplicated at this location" — same-named elements must be contiguous; in the repo file insert after the **last** `</fieldPermissions>` / `</recordTypeVisibilities>`. (b) Any profile you give `<recordTypeVisibilities>` for an object must end up with a **default** RT for that object (or all visible=false → master default) — adding a non-default RT to a profile that has NO Opportunity RT default errors "No default record type specified"; so put RT visibility only on profiles that already manage that object (here: `Admin` + `JCRC - Fundraising`), FLS-only on the rest. (c) Profile deploy is transactional — one profile's error rolls back all. **Given all this, prefer a PERMISSION SET for FLS** (JSI-122 pattern) unless the user specifically wants profiles. The 4 JCRC custom profiles are `JCRC - Development/Fundraising/Marketing/Volunteering`; System Administrator's file is `Admin.profile-meta.xml`.
- **Custom Metadata RECORDS need `xmlns:xsd` declared (JSI-89, 2026-06-25):** a `*.md-meta.xml` record using `<value xsi:type="xsd:string">`/`xsd:boolean` MUST declare **both** namespaces on the root: `<CustomMetadata xmlns="http://soap.sforce.com/2006/04/metadata" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:xsd="http://www.w3.org/2001/XMLSchema">`. Omitting `xmlns:xsd` (an undeclared prefix in the attribute *value*) makes the deploy fail two ways with NO useful message: **`sf` source deploy resolves "0 components"** (silently skips the files), and **MDAPI deploy throws server `UNKNOWN_EXCEPTION`**. Python `ElementTree` parses it as "OK" (it doesn't validate prefixes inside attribute values) so local XML checks won't catch it. **Fastest diagnosis:** create one record in the UI (Setup→CMDT→Manage Records), `sf project retrieve` it, and diff. The CMDT *type* deploying fine + SOQL working does NOT imply records will deploy. Field order in records is alphabetical on retrieve (not required for deploy).
- **Matching & duplicate rules (JSI-89, 2026-06-24):** `matchingRule` metadata is **one file per object** (`Contact.matchingRule-meta.xml`) holding ALL rules. It contains the **managed npsp__ rule**, which **can't be deployed** ("Cannot create a new component with the namespace: npsp") and `-m MatchingRule:...` flags the others as "Not in package.xml". **Fix:** deploy ONLY your rule from a **temp** `Contact.matchingRule-meta.xml` containing just it (matching-rule deploy is additive by `fullName`; managed rule untouched). Matching-rule **activation is async** (deploy runs long → use background). DuplicateRule **`sortOrder` must be sequential from 1** per object (existing contact dup rules used 1 & 2 → new one = 3). To power `Datacloud.FindDuplicates` **without** nagging users, make a **silent** duplicate rule: `actionOnInsert/Update=Allow`, `operationsOnInsert/Update=Report` (no Alert). FindDuplicates uses ALL active dup rules; the org's default contact rules are **email-driven** (name-alone won't match) — add a fuzzy-name matching rule if you need name matching. Record-triggered flow calling an invocable that updates the triggering record needs a **static Set recursion guard**.
- **Lookup to `User` can't be a REQUIRED foreign key (JSI-90, 2026-07-01):** a `<referenceTo>User</referenceTo>` lookup rejects `deleteConstraint` Cascade/Restrict ("Cannot add a lookup relationship child with cascade or restrict options to User"), but a **required** lookup *demands* a delete constraint ("must specify either cascade delete or restrict delete for required lookup foreign key") — so a required User lookup is impossible. **Fix:** make the User lookup `required=false` + `deleteConstraint=SetNull`, and enforce presence with a **validation rule** (`ISBLANK(User_Lookup__c)`). (Contact/other standard-object lookups DO support Restrict + required.)
- **Apex/Flow gotchas from the JSI-90 reconciler (2026-07-01):** (1) `map` AND `into` are **reserved** Apex identifiers — can't use as variable/param names ("Identifier name is reserved"); use `bucket`/`target`/etc. (2) To put an apostrophe inside an `@InvocableMethod`/`@InvocableVariable` string attribute, escape with **`\'`** — using `''` (SQL-style) silently splits the string and derails the whole class parse with misleading cascade errors ("Unexpected token '@'", "Invalid type: label", "Invalid constructor name: InvocableMethod"). (3) A record-triggered flow with `<triggerType>RecordBeforeDelete</triggerType>` ALSO requires `<recordTriggerType>Delete</recordTriggerType>` or deploy fails "field integrity exception ... you also need to set recordTriggerType." (4) A child lookup with `deleteConstraint=Restrict` does **NOT** block the parent's delete if a **before-delete** flow/trigger deletes the children first (verified) — good pattern for "cascade cleanup + let the parent delete." (5) A **reparentable** master-detail (`reparentableMasterDetail=true`) lets automation move a child to a different parent (e.g. move a gift's allocation to a different fiscal-year summary when Close Date changes) and both parents' roll-ups recalc.
- **Can't convert a field TYPE to Roll-Up Summary in place (JSI-90, 2026-07-01):** deploying a changed `<type>Summary</type>` over an existing Currency/Number field fails "Cannot update a field to a Summary from something else." **Fix:** delete the field and recreate it as Summary — and first delete anything that references it (e.g. a formula that sums it), else the delete is blocked. For a **master-detail child**, prefer a native Roll-Up Summary (with `<summaryFilterItems>` on a child picklist) over DLRS: real-time, delete/reparent-safe, version-controlled, no managed trigger artifacts.
- **Perm set must be ASSIGNED before anon-Apex compiles new fields (JSI-90, 2026-07-01):** deploying a permission set with `fieldPermissions` grants FLS, but the running user must be **assigned** that perm set (`sf org assign permset -n <Name>`) or anonymous Apex fails to compile with "Field does not exist: X__c on Y__c" (anon Apex is FLS-checked at compile for the running user). Assign, then run the savepoint→rollback verification.
- **Additive minimal-profile deploy only ADDS/enables perms — it does NOT revoke (JSI-122, 2026-07-08):** the stripped-`<Profile>` additive deploy technique (used for FLS/object/class grants) can turn permissions ON but **cannot turn them OFF** — deploying `<allowDelete>false</allowDelete>` over an existing `true` **leaves it `true`** (verified: 4 profiles kept Tag__c delete=true despite a false in the deploy). Same for downgrading FLS or viewAll/modAll. To **revoke** a profile permission you need a **full-profile replace deploy**, which in this org is blocked by the invalid-tab gotcha (see the FLS/RT-on-profiles entry). Practical consequence: profiles can only be *tightened* via the Setup UI or a full-profile deploy (tabs stripped) — not via the additive method. **Also: retrieving full profiles into the repo via the org "metadata snapshot" can silently grant `viewAllRecords`/`modifyAllRecords`=true on custom objects** — the JCRC custom profiles (Development/Marketing/Volunteering) carry **Modify All on ~117–129 objects** (near-admin), so any perm set scoped to those objects is redundant, and object-level "no delete" hardening is moot without a broader least-privilege pass. **When migrating a perm set → profiles, the real gap is usually FLS** (custom-object CRUD + Apex class access are often already on the profile from the snapshot; FLS ships `readable=false`).
- **NPSP Email Acknowledgment = managed WORKFLOW RULE, not a trigger/batch (JSI-87, 2026-07-08):** NPSP's native "acknowledge donations by email" feature is driven by the managed **workflow rule `npsp__Opportunity Email Acknowledgment`** on Opportunity (→ email alert `npsp__Opportunity_Email_Acknowledgment`, classic template `NPSP Opportunity Acknowledgment` in the `NPSP Email Templates` folder). It fires off the **`npsp__Acknowledgment_Status__c`** picklist — specifically the values **`Email Acknowledgment Now`** / **`Email Acknowledgment Not Sent`**, which are **NOT present by default** (admins add them per NPSP's setup guide; the "Email Acknowledgments" list-view button sets them). It is **NOT a TDTM trigger** (`npsp__Trigger_Handler__c` has no ack handler) and **NOT a scheduled batch** (no ack CronTrigger). To check state: `sf project retrieve start -m "Workflow:Opportunity"` and read `<rules>` `<active>` (in JCRC-Dev the rule is **`active=false`** — inactive). Managed workflow rule → **can't edit criteria** (clone to change), but activation is admin-controlled. **To guarantee a single custom ack engine:** keep the rule inactive + **deactivate the two `Email Acknowledgment…` picklist values** (managed field — likely Setup-UI). Native ack **fields** `npsp__Acknowledgment_Status__c`/`npsp__Acknowledgment_Date__c` are always present (values: To Be Acknowledged / Acknowledged / Do Not Acknowledge + the 2 email ones).
- **Record-triggered Flow gotchas (JSI-87, 2026-07-08 — a CMDT-driven router that classifies gifts; ALL of these produced a silently-non-firing or wrong-result flow, no deploy error):**
  1. **A loop-body Decision must connect EVERY outcome back to the loop element.** If the Decision's default ("no match") outcome has **no connector**, the flow **terminates mid-iteration** (and never reaches the loop's `noMoreValues`/post-loop path) → nothing happens. Both the match and no-match outcomes must point back to the `<loops>` element.
  2. **`IsWon` (and other formula/derived fields) don't work in record-triggered flow ENTRY `<filters>`.** The flow silently never fires. Gate entry on a **direct field** (e.g. a custom `Channel IsNull`) and move the `IsWon`/formula check into a **Decision** in the body (Decisions CAN read formula fields).
  3. **`NotEqualTo` in entry filters (and SOQL `!=`) EXCLUDES null-valued records.** A new record whose picklist is null will NOT match `Status NotEqualTo "X"`, so the flow won't fire. Use `EqualTo` inside a Decision (`EqualTo` on null = false → flows to default) instead of `NotEqualTo` at entry.
